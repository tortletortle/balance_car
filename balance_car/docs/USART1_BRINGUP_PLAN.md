# USART1 外设开启方案

## 1. 文档目的

本文档用于指导新项目中 `USART1` 的开启、验证、分层封装和后续扩展。

当前目标不是一次性把串口做成最终版本，而是分阶段完成：

- 先让 `USART1` 按 `STM32CubeIDE` 标准方式工作
- 再把它纳入项目分层架构
- 最后再扩展接收、中断和 DMA 能力

## 2. 为什么先做 USART1

在所有外设里，`USART1` 最适合作为第一个开启的外设，原因如下：

1. 它是系统最重要的“观测窗口”
2. 后续调试其他外设时都需要串口输出状态
3. 它最容易形成“可见结果”，有助于建立开发节奏
4. 它也是课程里最容易被问到的基础外设之一

因此，`USART1` 的作用不仅是“通信”，更是整个系统的调试基础设施。

## 3. 当前板级基线

根据已冻结的硬件基线，当前 `USART1` 引脚为：

- `PA9` -> `USART1_TX`
- `PA10` -> `USART1_RX`

这两个引脚已经在板级基线和旧工程中得到确认。

## 4. 分层架构中的位置

`USART1` 在项目架构中涉及三层：

### 4.1 `board` 层

负责：

- 在 `.ioc` 中配置 `USART1`
- 生成 `MX_USART1_UART_Init()`
- 完成引脚、时钟、中断、DMA 等基础资源配置

### 4.2 `drivers` 层

负责：

- 封装最基础的串口发送与接收能力
- 向上层隐藏 HAL 细节
- 提供统一的串口访问接口

建议文件：

- `drivers/drv_uart.h`
- `drivers/drv_uart.c`

### 4.3 `app` 层

负责：

- 用串口做启动信息输出
- 用串口做状态帧上报
- 后续承接命令协议输入

建议文件：

- `app/app_telemetry.h`
- `app/app_telemetry.c`
- `app/app_command.h`
- `app/app_command.c`

## 5. 开启策略

`USART1` 建议采用分阶段开启策略。

### 阶段 A：最小可用发送

目标：

- 上电后可以从串口看到固定文本

特征：

- 只做发送
- 不做接收
- 不做 DMA
- 不做复杂封装

推荐输出：

- `BOOT\r\n`
- 或 `USART1 OK\r\n`

这是最小成功标准。

### 阶段 B：基础接收能力

目标：

- 能接收外部发来的单字节或一小段数据

特征：

- 先使用简单方式实现
- 优先考虑阻塞或中断接收
- 先验证“收得到”，再讨论性能优化

### 阶段 C：工程化接收链路

目标：

- 为后续命令协议和状态系统提供稳定基础

特征：

- 可以加入环形缓冲区
- 可以引入中断接收
- 在确有必要时再引入 DMA 或 `ReceiveToIdle`

### 当前建议

为了符合你的学习目标和考试目标，当前建议先做到：

- **阶段 A + 阶段 B 的初版**

不要一开始就直接做 DMA 版本。

## 6. 为什么第一阶段不直接上 DMA

虽然旧项目已经使用了 `USART1 + DMA`，但新项目第一阶段不建议直接复制这个做法，原因如下：

1. 你现在的目标是理解，而不是最短时间达到复杂功能
2. 串口最开始只需要承担“可观测”作用
3. 一开始就上 DMA，会把学习难点混在一起：串口、DMA、空闲中断、缓冲管理、协议处理
4. 课程答辩时，先把 `USART` 基础原理讲清楚更重要

因此第一阶段建议：

- 先用 `STM32CubeIDE` 标准异步串口
- 先确保发送正常
- 再逐步加入接收和工程化封装

## 7. STM32CubeIDE 配置方案

在 `.ioc` 中建议这样配置：

### 7.1 外设模式

- `USART1`
- Mode: `Asynchronous`

### 7.2 串口参数

- Baud Rate: `115200`
- Word Length: `8 Bits`
- Stop Bits: `1`
- Parity: `None`
- Hardware Flow Control: `None`
- Mode: `TX_RX`
- Oversampling: `16`

### 7.3 引脚

- `PA9` -> `USART1_TX`
- `PA10` -> `USART1_RX`

### 7.4 中断

第一阶段建议：

- 可以先保留基础 `USART1` 中断能力，但不强依赖它完成首个验证

### 7.5 DMA

第一阶段建议：

- **先不开 DMA**

后续如果命令链路和上报负载增加，再单独做 DMA 升级。

## 8. Cube 生成后的预期文件

`STM32CubeIDE` 正常生成后，通常会涉及：

- `Core/Inc/usart.h`
- `Core/Src/usart.c`
- `Core/Src/main.c`

其中：

- `usart.c` 保存 `MX_USART1_UART_Init()`
- `main.c` 中会调用 `MX_USART1_UART_Init()`

后续我们自己的代码应建立在这套生成代码之上，而不是替代它。

## 9. 第一阶段推荐的软件结构

### 9.1 `board` 层

使用 `CubeIDE` 生成：

- `MX_USART1_UART_Init()`

### 9.2 `drivers/drv_uart`

第一阶段推荐接口：

- `DrvUart1_Write(const uint8_t *data, uint16_t len)`
- `DrvUart1_WriteText(const char *text)`
- `DrvUart1_WriteLine(const char *text)`

第一阶段不必一开始就设计复杂对象模型，先做简单、稳定、容易理解的接口。

### 9.3 `app/app_telemetry`

第一阶段推荐行为：

- 系统启动完成后发送一行启动信息
- 例如：`BOOT,USART1=OK`

这样做的目的：

- 形成最小闭环
- 明确区分“串口初始化成功”和“上层使用成功”

## 10. 数据流说明

当前阶段 `USART1` 的最小数据流如下：

1. `board` 初始化 `USART1`
2. `drivers/drv_uart` 调用 HAL 发送函数
3. `app/app_telemetry` 组织输出文本
4. 上位机串口助手显示文本

这个链路非常适合作为第一个系统级闭环。

## 11. 验证方案

### 11.1 硬件准备

- 板子正常上电
- `USART1_TX / USART1_RX / GND` 已接到 USB 转串口工具或调试链路
- 上位机串口工具已准备好

### 11.2 串口工具参数

- 波特率：`115200`
- 数据位：`8`
- 停止位：`1`
- 校验位：`None`

### 11.3 第一阶段验收方法

验收动作：

1. 烧录程序
2. 打开串口助手
3. 复位板子
4. 观察是否输出启动文本

验收通过标准：

- 复位后能稳定输出固定文本
- 输出内容可重复、可识别
- 不出现乱码

### 11.4 第二阶段验收方法

验收动作：

1. 上位机发送一个字符
2. 固件接收到后做简单响应
3. 上位机收到回显或响应文本

验收通过标准：

- 发送有响应
- 多次测试结果稳定

## 12. 常见问题与排查顺序

如果 `USART1` 不工作，建议按以下顺序排查：

1. 串口工具参数是否正确
2. `PA9/PA10/GND` 接线是否正确
3. `.ioc` 中是否真的是 `USART1 Asynchronous`
4. 系统时钟是否正常
5. `MX_USART1_UART_Init()` 是否真的被调用
6. 发送函数是否真的执行到
7. 是否因为没有 `\r\n` 导致串口工具看起来像没输出

## 13. 课程答辩可讲点

这一外设非常适合答辩时讲清楚以下内容：

### 13.1 为什么先做串口

- 串口是最基础的调试接口
- 它为后续所有外设调试提供观测能力

### 13.2 为什么用 `115200 8N1`

- 通用、兼容性高
- 对当前系统调试输出足够

### 13.3 为什么第一阶段不直接用 DMA

- 先保证原理和链路清晰
- 再做工程优化

### 13.4 为什么要分层

- `board` 配置资源
- `drivers` 封装发送能力
- `app` 使用串口做系统观测

## 14. 当前阶段验收标准

完成 `USART1` 第一阶段后，应满足：

- `.ioc` 已正确配置 `USART1`
- 上电后可以稳定输出一行文本
- 文本发送链路能用“分层架构”解释清楚
- 你自己能说清楚：
  - 引脚为什么是 `PA9/PA10`
  - 参数为什么是 `115200 8N1`
  - 为什么第一阶段不直接上 DMA
