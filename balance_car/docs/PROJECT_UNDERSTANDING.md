# 项目理解：`balance_v3` 参考整理

## 1. 目标说明

本文档用于整理 `D:\program\learning\balance_v3` 的结构、控制主线、硬件映射、测试资产和维护问题。

结论用途：

- 为新项目提供“理解基础”
- 为后续架构讨论提供上下文
- 避免再次直接依赖 AI 拼接出的黑盒结构

本文档不是迁移清单，也不是代码复用授权。

## 2. 旧项目整体判断

`balance_v3` 不是单一 STM32 固件，而是一整套实验型工程，包含：

- STM32CubeMX/HAL 固件主体
- 电机、编码器、IMU、电池、安全等底层模块
- 串口自动化测试脚本
- 参数扫描、离线筛参与文档归档脚本
- 大量 CSV/MD 实验记录

该工程已经具备“能跑 + 能测 + 能调”的完整链路，但工程中心过度集中在一个超大应用文件中，维护门槛高。

## 4. 主要固件模块

旧工程中可识别的核心模块如下：

- `adc_voltage`：电池电压采样与有效性判断
- `encoder_reader`：双路编码器增量读取
- `motor_driver`：PWM、方向、使能与斜坡更新
- `imu_mpu6050`：MPU6050 读取与姿态估计
- `soft_i2c`：软件 I2C 通信层
- `safety`：安全模式与故障闭锁
- `uart_command`：单字节串口命令队列与解析
- `balance_app`：应用总控、状态机、控制环、遥测、测试模式

其中 `balance_app` 是系统主脑，但也承担了过多职责。

## 5. 硬件映射结论

根据旧工程代码可确认的主要映射：

- 主控：`STM32F103C8T6`
- 控制节拍：`TIM1` 周期中断，5ms 基础调度
- 电机 PWM：`TIM3` 两路 PWM 输出
- 编码器：`TIM4` 和 `TIM2` 编码器模式
- 串口：`USART1`，`115200 8N1`，接收路径使用 `ReceiveToIdle DMA`
- IMU：`MPU6050`，使用软件 I2C 访问
- 电机驱动使能：`PA4`
- 急停输入：`PA5`
- 电机方向脚：`PB12/PB13/PB14/PB15`

这些映射说明旧工程已经形成了明确的底层资源占用方案，后续新架构需要先确认是否沿用这些分配。

## 6. 控制主线理解

### 6.1 启动路径

启动过程大致为：

1. CubeMX 初始化时钟、GPIO、ADC、TIM、USART
2. 应用层 `BalanceApp_Init()` 完成模块初始化
3. 启动编码器、PWM、基础定时器和串口 DMA 接收
4. 读取首个电池值，更新安全状态
5. 进入安全输出状态，并上报 `BOOT` 状态帧

### 6.2 主循环

主循环非常薄，只做一件事：重复调用 `BalanceApp_RunOnce()`。

`RunOnce()` 内部主要完成：

- 处理 tick 溢出故障
- 维护串口收发恢复
- 处理待执行串口命令
- 检查控制任务卡顿
- 从 tick 队列中追赶执行 5ms 控制任务

### 6.3 5ms 控制任务

5ms 控制任务是旧工程的控制中心，顺序大致为：

1. 读取编码器增量
2. 读取 IMU 并更新姿态缓存
3. 周期读取电池电压
4. 更新安全故障与安全模式
5. 若处于 `ARMED`，进入控制输出逻辑
6. 角度环输出 `speed_cmd`
7. 速度环把 `speed_cmd` 转成 `target_pwm`
8. 结合每个电机的起转辅助与地面协调逻辑
9. 输出到电机驱动

### 6.4 控制结构

旧工程控制结构可以概括为：

- 姿态外环：角度 `PID`，输出速度/力矩命令倾向
- 速度内环：速度 `PI`，结合前馈输出 PWM
- 驱动层：PWM 限幅、斜坡、起转补偿、左右电机协调

补充特性包括：

- 零偏自动捕获
- 在线零偏微调
- 大角度恢复区与硬切断区
- 人工大命令旁路角度环
- 离线测试保活窗口

## 7. 串口协议理解

旧工程采用单字节控制命令，便于台架脚本控制：

- `A` / `E`：ARM
- `T`：进入离线测试模式
- `D` / `S`：DISARM
- `+` / `-`：人工调整命令
- `K`：KEEPALIVE
- `C`：CLEAR FAULT
- `?` / `Q`：查询状态
- `Z`：写入角度零偏

状态输出为可解析文本帧，以 `STAT,...` 形式上报，字段包含：

- 安全模式
- 故障位
- 电池电压
- 左右 PWM
- 左右编码器增量
- IMU 新鲜度、姿态与角速度
- 角度环阻塞原因
- 速度目标、测量值、输出值
- 固件签名

这部分非常值得保留，因为它把“可控”和“可观测”建立起来了。

## 9. 旧工程的主要维护问题

### 9.1 过度集中

- `balance_app.c` 过大，承担了太多系统职责
- 控制、协议、安全、调试、测试模式耦合在同一层

### 9.2 参数体系复杂

- 大量宏定义集中在应用层
- 参数之间存在隐式耦合关系
- 改参数容易造成不可预期联动

### 9.3 实验痕迹太重

- 自动化、离线调参和临时辅助特性较多
- 对当前“重写并掌控结构”的目标来说，旧实现参考价值有限，旧结论参考价值更高

## 10. 对新项目的约束结论

当前阶段先形成以下约束：

- 不直接复制 `balance_v3` 的 `balance_app.c`
- 不直接继承其宏参数体系
- 不以“先跑起来”为优先，而以“先可理解、可维护”为优先
- 仅把旧工程作为参考资产库
